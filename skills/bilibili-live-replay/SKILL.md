# B 站直播录播与投稿

先确定本次要推进到哪一步，然后从已有检查点继续。录制、上传草稿、仅自己可见投稿、公开投稿是不同的终点；用户已明确授权的步骤直接执行，不重复索要确认。录制由用户明确指令手动启动，只处理当前一场；未开播或该场结束后退出，不定时查询开播、不等待下一场，也不创建候播定时任务。

## 入口与检查点

1. 读取当前工作区的状态、停止标记、媒体清单和投稿记录；核对 UID、房间号、日期、标题和现有 BVID / 草稿 ID，不能把参考稿件当作当前目标。只读取当前工作区的检查点；本技能不附带历史用户或稿件资料。
2. 复用现有后台进程、上传会话和稿件。用户已停止录制时保留停止标记，只有明确开始或恢复录制指令才能删除它；旧候播自动任务保持停用。
3. 将中间数据放 `work/`，交付的视频、歌曲轴、投稿文案、检查结果放 `outputs/`。准备 `work/replay-workflow.json` 记录 `phase`、`room`、`raw_files`、`final_media`、`media_check`、`axis`、`upload`、`draft_id`、`bvid`、`visibility_requested`、`visibility_verified`、`evidence` 和 `next_action`。只把观察到的状态写成已完成；不保存 Cookie、签名流地址或访问令牌。

## 按阶段加载

| 当前任务 | 先读 | 辅助脚本 |
|---|---|---|
| 手动接流、单场续录、停止或恢复 | [录制与恢复](references/recording.md) | `scripts/live_watch.py` |
| 结束录制、拼接、转封装、媒体检查 | [媒体处理](references/media.md) | `scripts/media_check.py` |
| 提取音频、识别歌曲、建立时间轴 | [歌曲时间轴](references/timeline.md) | `scripts/transcribe.py`、`scripts/axis.py` |
| 上传、草稿、封面文案、仅自己可见或公开 | [上传与发布](references/publishing.md) | 使用当前浏览器工具和实际界面 |

不要为了只改可见范围而重录、重新转写或重复上传。完整流程依次执行上述阶段；阶段交接时检查前一阶段的实际产物。

## 必须保留的边界

- “开始录制”须同时有正确的 FFmpeg 进程和持续增长的目标文件；进程已创建、事件名 `capture_started`、文件非零都不足以单独证明正在录制。
- 接口异常不能当作下播。恢复当前录制前核对旧 FFmpeg；同一 PID 和文件的接管不重复报告开始。断流后保留各原始片段，不能宣称无缺失。
- 转封装成功、`ffprobe` 成功、完整解码成功是三个不同证据；完整解码通过也不能证明没漏录。报告实际做过的检查及未覆盖的部分。
- 时间戳以最终上传的视频为零点，不能用直播墙上时间、ASR 分块时间或未裁剪原片时间替代。改过文件后重新绑定并核对。
- 转写只提供候选歌词和口播线索。歌名、歌手、串烧与重复演唱须有证据；拿不准就标注待核对，不用模型猜测填满时间轴。
- 上传字节 100% 不等于服务器“上传完成”；保存草稿必须回到草稿列表并重新打开验证。稿件投递成功不等于审核、转码完成或公开可播放。
- 沿用用户对当前稿件的发布及可见范围授权。草稿授权不包含投稿；私密投稿授权不包含公开。若已明确说“公开”，执行并验证即可。评论、置顶歌曲轴另按用户指令；不要自动重复发评论。

## 交付

报告当前终点和可访问链接；说明媒体时长、大小、已知缺口与检查范围。草稿给出可重新打开的草稿位置；投稿给出 BVID 和当前审核/转码/可见范围证据。避免把“已提交公开设置”写成已确认所有访客可播放。

使用技能内脚本前先运行对应 `--help`。脚本是本地工具，不会自行上传或投稿。观察到平台接口或界面变化时更新操作方法，保留报错事实，不伪造成功状态。
