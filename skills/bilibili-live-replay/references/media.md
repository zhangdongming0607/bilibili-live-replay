# 媒体准备与真实检查

## 先确定录制已结束

对照录制状态、FFmpeg PID / 完整命令和两次文件大小。仍在增长的文件不能当作最终上传版；要提前预览时明确它仍在写。将最终片段清单、录制范围和已知中断写入检查记录。

## 保留原件，生成投稿版

- 单片段且无需剪辑：`ffmpeg -nostdin -n -i 原片.mp4 -map 0:v:0 -map 0:a:0? -c copy -movflags +faststart 投稿版.mp4`。这会转封装，不会修复损坏帧或补回漏录。
- 多片段：先逐个 `ffprobe` 比较 codec、分辨率、音轨、采样率等。兼容时用 concat demuxer 的清单按真实顺序拼接；清单路径要按 FFmpeg concat 规则转义，不把路径直接拼进 shell。`-safe 0` 只用于自己生成并检查过的本地清单。规格不同或拼接有时间戳异常时单独处理并验证，不默默重编码掩盖问题。
- 转码/拼接/裁剪都输出新文件，不覆盖原件。不要同时把原片和内容相同的合并版上传成重复分 P。
- “完整回放单文件”“按录制片段多 P”“按单曲剪辑多 P”“每首单独稿件”是不同交付。沿用用户选择，不能用歌曲导航区间代替纯歌曲剪辑。

## 检查命令

```sh
python3 "$SKILL_DIR/scripts/media_check.py" --media "$FINAL_MEDIA" --report "$WORKSPACE/outputs/投稿准备/录播检查结果.json" --full-decode
```

默认仅 ffprobe 元数据；`--full-decode` 用 FFmpeg 将完整音视频解码到 null，记录返回码和错误日志。报告会绑定路径、大小、mtime 与媒体时长，保留探测警告，并明确不验证直播覆盖完整性。命令失败时仍查看生成的报告和日志；不要根据输出文件存在就声称检查成功。

完整解码可能耗时较长，用工具的异步会话等待并报告真实进度，别重复启动。出现 Invalid NAL unit size、缺失音轨、解码错误或异常时长，定位时间边界和原始片段；保留错误证据。如果修复或跳过了损坏部分，注明被删时间范围及对歌曲轴的影响。

最终上传文件再做媒体探测。若仅在原片做过完整解码、最终版只做探测，报告这一区别；不要把原片检查结果当成最终文件完整解码结果。完整解码通过仍不能证明没漏掉直播开头、断线时段或尾部。

交付最少包含最终视频、检查 JSON、投稿信息。文案区分文件时长与直播时长，并写清中途开始、断流、尾部截断或尚未人工逐段检查的范围。
